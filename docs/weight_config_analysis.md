# Gladiator Weight Configuration Analysis

## HLIL Observations

- The loader allocates a 0x404-byte block for the weight configuration, zeroes the entry count at offset 0, and repeatedly pulls tokens from the script precompiler. Each valid `weight` block appends a name pointer and associated tree handle; hitting 0x80 entries triggers the `"too many fuzzy weights\n"` error observed in the binary.【F:dev_tools/gladiator.dll.bndb_hlil.txt†L42083-L42171】
- Weight definitions begin with the literal `weight "<name>"` followed by a fuzzy definition or switch block. Invalid identifiers emit `"invalid name %s\n"` and the parser aborts by freeing the partially built config.【F:dev_tools/gladiator.dll.bndb_hlil.txt†L42123-L42174】
- When encountering nested `switch` constructs the parser defers to helper routines that print `"} //end case\n"` / `"} //end default\n"` markers, while the Gladiator writer closes each top-level block with `"} //end itemweight\n"`. Failure paths converge on diagnostics like `"can't merge weight configs\n"` during configuration merges.【F:dev_tools/gladiator.dll.bndb_hlil.txt†L42175-L42248】【F:dev_tools/gladiator.dll.bndb_hlil.txt†L42380-L42462】【F:dev_tools/gladiator.dll.bndb_hlil.txt†L42884-L42938】
- Fuzzy branch interpolation preserves the original integer division quirk: the inventory delta and case-range divisor are divided as integers before conversion to float. Negative return values warn with `"negative value set to zero\n"` but then use the following numeric token, matching both HLIL and the Quake III source.【F:dev_tools/gladiator.dll.bndb_hlil.txt†L41564-L41621】【F:dev_tools/gladiator.dll.bndb_hlil.txt†L42578-L42624】【F:dev_tools/Quake-III-Arena-master/code/botlib/be_ai_weight.c†L54-L70】【F:dev_tools/Quake-III-Arena-master/code/botlib/be_ai_weight.c†L579-L609】
- Consumers that request multiple configurations log size statistics (`"%6d bytes item weights\n"`, `"%6d bytes weapon weights\n"`) before storing item/weapon indices. Missing data yields `"couldn't load weights\n"` and cascades into `"item info %d \"%s\" has no fuzzy weight"` when a character profile references a non-existent block.【F:dev_tools/gladiator.dll.bndb_hlil.txt†L32481-L32489】【F:dev_tools/gladiator.dll.bndb_hlil.txt†L38348-L38380】【F:dev_tools/gladiator.dll.bndb_hlil.txt†L37080-L37168】

## Comparison with Quake III Arena

- Quake III’s `ReadWeightConfig` performs the same token loop, limiting configurations to 128 weights and reporting identical diagnostics when a switch block lacks a default or exceeds bounds. Its `weightFileList` cache is retained while `bot_reloadcharacters` is false and flushed by `BotShutdownWeights`, which matches Gladiator’s retained loader surface.【F:dev_tools/Quake-III-Arena-master/code/botlib/be_ai_weight.c†L153-L209】【F:dev_tools/Quake-III-Arena-master/code/botlib/be_ai_weight.c†L292-L433】【F:dev_tools/Quake-III-Arena-master/code/botlib/be_ai_weight.c†L896-L913】
- The recursive `FreeWeightConfig2` path frees each fuzzy separator and the owning name string, while `FreeWeightConfig` is conditional on `bot_reloadcharacters`. This matches the cached ownership split used by the Quake III successor and now mirrored by the reconstructed wrapper layer.【F:dev_tools/Quake-III-Arena-master/code/botlib/be_ai_weight.c†L112-L146】【F:dev_tools/Quake-III-Arena-master/code/botlib/be_ai_weight.c†L139-L146】【F:dev_tools/gladiator.dll.bndb_hlil.txt†L41685-L41735】
- Gladiator’s two-config merge routine enforces identical weight counts prior to averaging balance leaf nodes in the first config, using the short `"can't merge weight configs\n"` diagnostic on mismatch. The reconstructed `MergeWeightConfigs` keeps that surface separate from the Quake III-style three-config `InterbreedWeightConfigs` helper used by goal fuzzy logic.【F:dev_tools/gladiator.dll.bndb_hlil.txt†L42884-L42938】【F:dev_tools/Quake-III-Arena-master/code/botlib/be_ai_weight.c†L823-L876】【F:src/botlib/ai_weight/ai_weight.c】

## Integration Notes

- Parsing relies on the lightweight script precompiler: token fetches route through the `PC_*` style wrappers currently prototyped in `src/botlib/precomp/l_precomp.h`. The HLIL shows repeated calls to functions equivalent to `PC_ReadToken` and `PC_ExpectTokenString`, so a faithful implementation must sit on top of that interface when the lexer lands.【F:dev_tools/gladiator.dll.bndb_hlil.txt†L42083-L42248】【F:src/botlib/precomp/l_precomp.h†L8-L89】
- Memory management maps directly to the botlib allocator wrappers restored under `src/botlib/common/l_memory.c`. Allocation sites call helpers that resemble `GetClearedMemory`/`AllocMemory`, while cleanup paths dispatch to a `FreeMemory` analogue. The final implementation should therefore use the l_memory API to remain ABI-compatible with other bot subsystems.【F:dev_tools/gladiator.dll.bndb_hlil.txt†L42083-L42174】【F:src/botlib/common/l_memory.c†L1-L120】
- Weight consumers (goal selection, weapon evaluation) expect both configuration handles and indexed lookup tables. The bridge now wires `BotFindFuzzyWeight` and `BotFuzzyWeightHandle` alongside load/write/set helpers so q2bridge callers can resolve names once and evaluate indexed fuzzy trees without reaching into private config internals.【F:dev_tools/Quake-III-Arena-master/code/botlib/be_ai_weight.h†L47-L93】【F:src/botlib/ai_weight/bot_weight.c】【F:src/q2bridge/botlib.h】
- Struct-table consumers such as `ai_weapon` parse numeric token text directly instead of depending on optional lexer value caches. This keeps symbolic include expansion from `inv.h` faithful for fields such as `weaponindex`, `ammoindex`, spread, and activation timing even when the precompiler is built without cached token values.【F:src/botlib/common/l_struct.c】【F:dev_tools/assets/weapons.c】
