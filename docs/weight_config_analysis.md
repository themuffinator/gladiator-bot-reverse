# Gladiator Weight Configuration Analysis

## HLIL Observations

- The loader allocates a 0x404-byte block for the weight configuration, zeroes the entry count at offset 0, and repeatedly pulls tokens from the script precompiler. Each valid `weight` block appends a name pointer and associated tree handle; hitting 0x80 entries triggers the `"too many fuzzy weights\n"` error observed in the binary.【F:dev_tools/gladiator.dll.bndb_hlil.txt†L42083-L42171】
- Weight definitions begin with the literal `weight "<name>"` followed by a fuzzy definition or switch block. Invalid identifiers emit `"invalid name %s\n"` and the parser aborts by freeing the partially built config.【F:dev_tools/gladiator.dll.bndb_hlil.txt†L42123-L42174】
- When encountering nested `switch` constructs the parser defers to helper routines that print `"} //end case\n"` / `"} //end default\n"` markers, while the Gladiator writer closes each top-level block with `"} //end itemweight\n"`. Failure paths converge on diagnostics like `"can't merge weight configs\n"` during configuration merges.【F:dev_tools/gladiator.dll.bndb_hlil.txt†L42175-L42248】【F:dev_tools/gladiator.dll.bndb_hlil.txt†L42380-L42462】【F:dev_tools/gladiator.dll.bndb_hlil.txt†L42884-L42938】
- Fuzzy branch interpolation preserves the original integer division quirk: the inventory delta and case-range divisor are divided as integers before conversion to float. Negative return values warn with `"negative value set to zero\n"` but then use the following numeric token, matching both HLIL and the Quake III source. The undecided variant samples selected balance ranges with Q3's `(rand() & 0x7fff) / 0x7fff` scale during traversal but still returns the stored leaf weight after falling off the final separator, preserving the Q3 helper's asymmetry.【F:dev_tools/gladiator.dll.bndb_hlil.txt†L41564-L41621】【F:dev_tools/gladiator.dll.bndb_hlil.txt†L42578-L42660】【F:dev_tools/Quake-III-Arena-master/code/botlib/be_ai_weight.c†L54-L70】【F:dev_tools/Quake-III-Arena-master/code/botlib/be_ai_weight.c†L579-L637】【F:dev_tools/Quake-III-Arena-master/code/game/q_shared.h†L750-L751】
- `sub_10035fa0` copies the caller-supplied weight filename into a fixed buffer before any file work. The missing-file branch prints `"couldn't find %s\n"`, while the source-load failure branch preserves Gladiator's typo `"counldn't load %s\n"`; both diagnostics report that caller-facing path buffer rather than a higher-level wrapper string.【F:dev_tools/gladiator.dll.bndb_hlil.txt†L42072-L42080】【F:src/botlib/ai_weight/ai_weight.c】
- Consumers that request multiple configurations log size statistics (`"%6d bytes item weights\n"`, `"%6d bytes weapon weights\n"`) before storing item/weapon indices. Missing data yields `"couldn't load weights\n"` and cascades into `"item info %d \"%s\" has no fuzzy weight"` when per-client setup resolves a character weight filename to a config without the required item block. ## Comparison with Quake III Arena

- Quake III's `ReadWeightConfig` performs the same token loop, limiting configurations to 128 weights and reporting identical diagnostics when a switch block lacks a default or exceeds bounds. Missing-default switches append an implicit zero-weight separator with the retail max inventory sentinel, and overweight configs keep the first 128 entries before stopping. Its `weightFileList` cache is checked by caller filename before `LoadSourceFile`, retained while `bot_reloadcharacters` is false, and flushed by `BotShutdownWeights`. Cached Q3-style consumers continue to pass the original script name into `ReadWeightConfig`. Gladiator client setup deliberately takes a different, canonical ownership path: `BotSetupClient` calls `AI_GoalBotlib_LoadItemWeights`, which reaches the goal core's `BotLoadItemWeights` and `ReadWeightConfigUncached`; the extended export currently aliases that adapter, but its public name is not evidence of setup caching. Weapon weights use `BotLoadWeaponWeightsFresh`. Both loaders consume raw characteristic strings and never store either config on the character definition.【F:dev_tools/Quake-III-Arena-master/code/botlib/be_ai_weight.c†L153-L209】【F:dev_tools/Quake-III-Arena-master/code/botlib/be_ai_weight.c†L292-L433】【F:dev_tools/Quake-III-Arena-master/code/botlib/be_ai_weight.c†L896-L913】【F:dev_tools/gladiator.dll.bndb_hlil.txt†L32494-L32522】【F:src/botlib/ai_goal/bot_goal.c】【F:src/botlib/ai_weapon/bot_weapon.c】【F:src/botlib/interface/bot_interface.c】
- The recursive `FreeWeightConfig2` path frees each fuzzy separator and the owning name string, while `FreeWeightConfig` returns immediately whenever `bot_reloadcharacters` is false, even for direct non-cacheable loads. This matches the cached ownership split used by the Quake III successor; callers that must tear down a retained config use the force-free path or `BotShutdownWeights`.【F:dev_tools/Quake-III-Arena-master/code/botlib/be_ai_weight.c†L112-L146】【F:dev_tools/Quake-III-Arena-master/code/botlib/be_ai_weight.c†L139-L146】【F:dev_tools/gladiator.dll.bndb_hlil.txt†L41685-L41735】
- Gladiator’s two-config merge routine enforces identical weight counts prior to averaging balance leaf nodes in the first config, using the short `"can't merge weight configs\n"` diagnostic on mismatch. Its child-branch recursion passes the second config child as both arguments, and the sibling walk checks the second config's `next` pointer in the inverted retail direction, so multi-case switches stop after the first sibling path instead of fully merging the list. These quirks are pinned separately from the Quake III-style three-config `InterbreedWeightConfigs` helper used by goal fuzzy logic.【F:dev_tools/gladiator.dll.bndb_hlil.txt†L42884-L42938】【F:dev_tools/Quake-III-Arena-master/code/botlib/be_ai_weight.c†L823-L876】【F:src/botlib/ai_weight/ai_weight.c】
- Gladiator’s mutation helper follows the same random step shape as Quake III, but the retail DLL clamps mutated balance weights back to the existing `[min,max]` range instead of expanding the range to include the mutation. This keeps `EvolveWeightConfig` bounded after each mutation pass.【F:dev_tools/gladiator.dll.bndb_hlil.txt†L42721-L42775】【F:dev_tools/Quake-III-Arena-master/code/botlib/be_ai_weight.c†L706-L737】【F:src/botlib/ai_weight/ai_weight.c】
- `sub_10036e30` and `sub_10036eb0` map to the low-level scaling helpers: the leaf helper computes `(max + min) * scale` and clamps to the balance range, while the named wrapper clamps its incoming scale to `[0,1]` before walking the weight table. These helpers remain available for source parity, but Q3's public `BotMutateGoalFuzzyLogic` ignores its `range` parameter and dispatches directly to `EvolveWeightConfig`; the goal wiring now follows that shape and interbreeds into the child state's existing item-weight config instead of cloning a parent config.【F:dev_tools/gladiator.dll.bndb_hlil.txt†L42797-L42878】【F:dev_tools/Quake-III-Arena-master/code/botlib/be_ai_goal.c†L222-L260】【F:src/botlib/ai_goal/bot_goal.c】

## Integration Notes

- Parsing relies on the lightweight script precompiler: token fetches route through the `PC_*` style wrappers currently prototyped in `src/botlib/precomp/l_precomp.h`. The HLIL shows repeated calls to functions equivalent to `PC_ReadToken` and `PC_ExpectTokenString`, so a faithful implementation must sit on top of that interface when the lexer lands.【F:dev_tools/gladiator.dll.bndb_hlil.txt†L42083-L42248】【F:src/botlib/precomp/l_precomp.h†L8-L89】
- The precompiler must build with the Quake III `NUMBERVALUE` path enabled. Gladiator's default `fw_items.c` and `fw_weap.c` macros emit `$evalfloat(...)` expressions such as `POWERUP_SCALE(W_QUAD)`, and the dollar-eval directive copies `token.intvalue` / `token.floatvalue` into the expanded numeric token.【F:dev_tools/Quake-III-Arena-master/code/botlib/l_script.h†L34-L35】【F:dev_tools/Quake-III-Arena-master/code/botlib/l_precomp.c†L2576-L2596】【F:dev_tools/assets/fw_items.c†L18-L21】
- Defined-weight loads use the precompiler global-define list as a scoped setup hook before `PC_LoadSourceFile` copies those defines into the source. The cleanup must unlink each temporary define, because later asset loads such as `defaul_i.c` and `defaul_w.c` pass through the same global list when resolving `DMFLAGS` branches.【F:src/botlib/ai_weight/ai_weight.c】【F:src/botlib/precomp/l_precomp.c】【F:dev_tools/assets/fw_items.c†L41-L45】
- Memory management maps directly to the botlib allocator wrappers restored under `src/botlib/common/l_memory.c`. Allocation sites call helpers that resemble `GetClearedMemory`/`AllocMemory`, while cleanup paths dispatch to a `FreeMemory` analogue. The final implementation should therefore use the l_memory API to remain ABI-compatible with other bot subsystems.【F:dev_tools/gladiator.dll.bndb_hlil.txt†L42083-L42174】【F:src/botlib/common/l_memory.c†L1-L120】
- Weight consumers (goal selection, weapon evaluation, and retail client setup) expect both configuration storage and indexed lookup tables. Goal item scoring uses Q3's `UNDECIDEDFUZZY` path through `FuzzyWeightUndecided`, while the bridge wires `BotFindFuzzyWeight` and `BotFuzzyWeightHandle` alongside load/write/set helpers so q2bridge callers can resolve names once and evaluate indexed fuzzy trees without reaching into private config internals. Cache-retention regressions remain on the low-level and explicitly cached paths. Retail setup regressions instead prove fresh ownership and partial-failure behavior: same-character clients receive different goal-owned item configs and weapon-state-owned weapon configs; normal item/weapon/chat failures do not centrally destroy or reset the inactive client state; and retry reuses retained goal, weapon, and chat owners. The weapon-failure branch frees that attempt's item weights, and the chat-failure branch frees that attempt's item and weapon weights, while retaining the owner handles/objects. Final client teardown is chat → weapon → goal/item → character → console waypoints before successor-only states, and shutting down one complete client leaves another client's resources valid.【F:dev_tools/Quake-III-Arena-master/code/botlib/be_ai_weight.h†L47-L93】【F:dev_tools/gladiator.dll.bndb_hlil.txt†L32494-L32570】【F:src/botlib/ai_weight/bot_weight.c】【F:src/botlib/ai_goal/bot_goal.c】【F:src/botlib/ai_weapon/bot_weapon.c】【F:src/botlib/interface/bot_interface.c】【F:src/q2bridge/botlib.h】【F:tests/ai/test_ai_weight.c】【F:tests/ai/test_ai_weapon.c】【F:tests/ai/test_ai_character.c】
- Weapon weights preserve the Gladiator load order from `sub_10035340`: the fuzzy weight file is read first and stored on the weapon state, then the active weaponconfig is checked before building the per-weapon index table. `AI_LoadWeaponWeights` and `BotLoadWeaponWeights` can hold an unbound config for later `AI_WeaponWeightsBindConfig`, while the retail `BotLoadWeaponWeightsFresh` path gives each client weapon state its own allocation and reuses that state across setup retries; no setup reset or character-profile borrowing is involved. A raw empty filename fails directly rather than selecting the successor default. Selection refreshes stale bindings against the current global weaponconfig before scoring, consumes the live client/inventory/current-model sync from `sub_10020fe0`, preserves the existing selected weapon when no candidate wins, and applies the `activate + 3.0` delay until `sub_10035640` resets selector state while retaining the state-owned weight pointer.【F:dev_tools/gladiator.dll.bndb_hlil.txt†L26914-L26921】【F:dev_tools/gladiator.dll.bndb_hlil.txt†L41384-L41405】【F:dev_tools/gladiator.dll.bndb_hlil.txt†L41474-L41536】【F:src/botlib/ai/ai_weapon.c】【F:src/botlib/ai_weapon/bot_weapon.c】【F:tests/ai/test_ai_weapon.c】【F:tests/ai/test_ai_character.c】
- Struct-table consumers such as `ai_weapon` parse numeric token text directly instead of depending on optional lexer value caches.
